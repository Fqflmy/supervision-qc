# 角色权限审计与设计说明

> 审计对象：v1.0.0（commit `354d687`）
> 审计方式：**实测**（逐角色调真实接口）+ 代码核对，不只看权限表
> 配套：[部署运维手册 9.5](部署运维手册.md) · [上线流程与就绪度评估](上线流程与就绪度评估.md)

## 1. 四个角色的职责定位

| 角色 | 定位 | 核心动作 | 落地页 |
| --- | --- | --- | --- |
| **系统管理员** `admin` | 平台管理员 | 用户与项目授权、系统配置、审计 | 用户与授权 |
| **监理工程师** `engineer` | 一线执行者 | 上传规范材料、**发起质量评估**、看报告 | 评估任务 |
| **审核人员** `expert` | 质量把关者 | **人工复核**、确认结论、触发 LLM 评审 | 质量评审 |
| **普通用户** `viewer` | 只读使用者 | 查询授权范围内的报告与规范 | 运行总览 |
| *知识库管理员* `kb_manager` | 规范库维护者 | 上传/解析规范、构建知识图谱 | 知识库管理 |

> `kb_manager` 在权限表中存在，但**种子数据未创建该账号**，登录页也不提供 —— 属实现缺口。

### 1.1 能力矩阵（实测）

`有` = 该角色可调用对应接口；`无` = 403。

| 能力 | 所需权限 | admin | kb_manager | engineer | expert | viewer |
| --- | --- | :---: | :---: | :---: | :---: | :---: |
| 上传 / 解析规范 | `kb:write` | 有 | **有** | 无 | 无 | 无 |
| 构建知识图谱 | `kg:write` | 有 | **有** | 无 | 无 | 无 |
| 浏览规范（列表/详情/检索） | `kb:read` | 有 | 有 | 有 | 有 | **有** |
| 智能问答 | `retrieval:read` | 有 | 有 | 有 | 有 | 有 |
| **发起质量评估** | `eval:write` | 有 | 无 | **有** | 无 | 无 |
| **确认评估结论 / 复核** | `eval:review` | 有 | 无 | 无 | **有** | 无 |
| 触发 LLM 评审打分 | `judge:write` | 有 | 无 | 无 | **有** | 无 |
| 查看评估报告 | `eval:read` | 有 | 有 | 有 | 有 | 有 |
| 管理用户与项目 | `admin:*` | **有** | 无 | 无 | 无 | 无 |
| 审计日志 / 运行配置 | `admin:*` | **有** | 无 | 无 | 无 | 无 |

**设计合理性点评**：责任分离是成立的 —— 发起评估（`eval:write`）与确认结论（`eval:review`）
分属不同角色，符合「执行与审核分离」的质量管理原则；规范维护（`kb:write`/`kg:write`）
独立于业务角色，避免一线人员随意改规范库。

## 2. 实测发现的问题

### 2.1 🔴 工程师无法实际发起评估（可用性缺口，非权限问题）

**现象**：`engineer` 调 `POST /eval/tasks` 返回 **403**，报错为

```
非管理员创建任务必须指定 project_id（且需在授权项目范围内）
```

**根因**：为修复越权，我上几轮给创建任务加了项目校验 —— 非管理员必须显式传
`project_id`。但**没有任何接口让普通用户知道自己被授权了哪些项目**
（`GET /admin/projects` 是管理员专属，`GET /me/scope` 当时只返回 ID 列表、不含项目名称）。

**后果**：工程师即使有 `eval:write` 权限，也**无法在实际操作中创建任务** ——
他不知道该传哪个 ID；前端也没有项目下拉。这是「权限给了但功能走不通」。

**修法**：
1. 新增 `GET /me/projects` 返回当前用户被授权项目的 `id/code/name`（普通用户可调）；
2. 创建任务时，若用户只被授权一个项目且未传 `project_id`，**自动采用该项目**；
3. 前端「新建评估任务」表单增加项目选择（仅当授权项目 > 1 时必选）。

### 2.2 🔴 `POST /eval/feedback` 缺少权限校验（越权）

**现象**：该接口只要求登录（`CurrentUser`），注释写的是「专家复核反馈」。
**任何登录用户**（含只读用户 `viewer`）都能提交人工复核意见。

**后果**：只读角色可写入复核结论，污染质量记录 —— 与
`/tasks/{id}/resume` 要求 `eval:review` 的强度不一致，属明显的遗漏。

**修法**：改为要求 `eval:review`（与同类端点一致）。

### 2.3 🟠 审核人员没有「待复核队列」

**现象**：审核人员的核心工作是处理待复核任务，但目前只能：
- 在评估任务列表里按状态筛 `NEED_HUMAN`；
- 进入单个任务详情后点「提交复核」。

**缺失**：没有专门的「待我复核」入口与计数。`GET /eval/tasks?state=NEED_HUMAN`
已支持按状态筛选，但前端未为审核角色提供快捷入口。

**影响**：审核人员不明确「现在该处理哪些」，属**不完善**。

### 2.4 🟠 普通用户看不到知识库内容

**现象**：`viewer` 有 `kb:read`，`GET /kb`、`GET /kb/documents` 均返回 200，
但菜单**不显示「知识库管理」**（该项要求 `kb:write`）。

**后果**：只读用户**有权限浏览规范，却没有任何界面入口**。对监理场景来说，
「查规范」是基本诉求。

**修法**：把知识库页按权限分级 —— 有 `kb:write` 显示完整管理功能，
仅有 `kb:read` 显示只读浏览（列表/详情/检索），菜单对只读角色也开放。

### 2.5 🟠 `kb_manager` 角色不可用

**现象**：权限表与菜单规则都覆盖了 `kb_manager`，但：
- 种子数据不创建该账号；
- 登录页不提供该身份；
- `test_role_matrix.py` 的菜单契约里也没有它。

**后果**：这是一个「文档里有、实际用不到」的角色。

**修法（二选一）**：① 种子数据补建 `kb_manager` 账号并加入登录页；
② 明确该角色为「预留」，在文档与权限表中标注。

### 2.6 🟡 权限点语义不一致

| 权限点 | 语义 | 现状 |
| --- | --- | --- |
| `judge:read` | 阅读评审结果 | 所有角色都有 |
| `judge:write` | 触发评审打分 | 仅 `expert` / `admin` |
| `eval:review` | 人工复核确认 | 仅 `expert` / `admin` |

`eval:review` 与 `judge:write` 在两个接口上都由同一组角色持有，
但 `/tasks/{id}/resume` 要求前者、`/reports/{id}/score` 要求后者，
**同一个业务动作（复核）却要两个权限点**，容易在新增接口时选错。

**修法**：统一为 `eval:review`，或明确二者边界并写入文档。

## 3. 完善度结论

| 维度 | 评价 |
| --- | --- |
| 责任分离 | ✅ 合理：发起 / 复核 / 规范维护 / 只读四者边界清晰 |
| 后端权限边界 | ⚠️ 一处越权（`/eval/feedback`），其余正确 |
| 前端可见性 | ⚠️ 与后端有错位（只读角色有 `kb:read` 无入口） |
| 端到端可走通 | ❌ 工程师**无法实际发起评估**（缺项目上下文） |
| 角色完整性 | ⚠️ `kb_manager` 不可用；审核人员缺待办入口 |

**总体判断：权限模型设计合理，但功能不完善** —— 存在 2 个必须修的问题
（2.1 工程师无法发起评估、2.2 复核反馈越权）与 3 个影响体验的缺口。

## 5. 复现方式

```bash
# 逐角色实测权限边界（需服务已启动）
docker compose exec api python scripts/audit_roles.py --base http://127.0.0.1:8000

# 权限点覆盖核对（纯代码，不需服务）
python backend/scripts/audit_roles.py --help
```

审计脚本会用**真实参数**探测（不是空 body）——
这点很关键：用空 body 会拿到 422，容易被误读为「无权限」。
