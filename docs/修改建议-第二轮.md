## 2. P0：功能走不通 / 安全边界缺失

### 2.1 工程师无法实际发起评估（功能断点）

**现象**

```bash
# engineer 身份
POST /api/v1/eval/tasks
→ 403 {"message":"非管理员创建任务必须指定 project_id（且需在授权项目范围内）"}
```

**根因**

为修复越权，创建任务时对非管理员加了项目校验：必须显式传 `project_id` 且在自己被授权的项目内。
但**没有任何接口让普通用户知道自己被授权了哪些项目**：

| 接口 | 可访问角色 | 返回内容 |
| --- | --- | --- |
| `GET /admin/projects` | 仅管理员 | 全部项目 |
| `GET /me/scope` | 所有登录用户 | `project_ids: [3]`（**只有 ID，没有名称**） |

**后果**：工程师有 `eval:write` 权限，却不知道该传哪个数字；前端也没有项目下拉。
这是「权限给了但流程走不通」，属最严重的一类问题。

**建议**

| # | 改动 | 位置 |
| --- | --- | --- |
| 1 | 新增 `GET /me/projects`，返回当前用户被授权项目的 `id / code / name` | `routes/users.py`（与 `/me/scope` 同处） |
| 2 | 创建任务时，若用户**只被授权一个项目**且未传 `project_id`，**自动采用之**（多项目时仍要求显式指定） | `routes/eval.py` |
| 3 | 前端「新建评估任务」表单增加项目选择；仅当授权项目 > 1 时标记为必填 | `views/EvaluationView.vue` |

**第 2 条尤其重要**：它让「只有一个项目」的常见情形无需任何额外配置即可使用，
同时不放松多项目场景下的隔离。

**验收**：`engineer` 账号登录 → 不选项目也能创建任务 → 任务出现在自己列表中。

### 2.2 `POST /eval/feedback` 缺少权限校验（越权）

**现象**：该接口只要求登录（`CurrentUser`），而接口注释写的是「专家复核反馈」。

```
POST /api/v1/eval/feedback   ← 任何登录用户都能调用
```

**后果**：**只读用户（viewer）也能提交人工复核意见**，污染质量记录。
同类端点 `/tasks/{id}/resume` 要求 `eval:review`，这个漏了 —— 属明显遗漏而非有意设计。

**建议**：改为 `require_permission("eval:review")`。

**验收**：`viewer` 调用返回 403；`expert` / `admin` 正常提交。

## 3. P1：可用性与角色完整性

### 3.1 普通用户看不到规范（有权限无入口）

**现象**：`viewer` 有 `kb:read`，`GET /kb`、`GET /kb/documents` 均 200，
但菜单只有「智能问答」——**没有任何浏览规范的入口**。

**为什么要改**：监理场景里「查规范」是基本诉求。让只读用户只能通过问答间接获取，
体验上说不通（他能查到，但没有列表可看）。

**建议**（二选一）

| 方案 | 做法 | 影响面 |
| --- | --- | --- |
| **A. 复用知识库页** | 菜单与路由改 `kb:read`；页面内已有 `canWriteKb` 控制写操作，天然支持只读 | 小（只改 2 处权限声明；菜单名建议改为「知识库」） |
| B. 新增「规范查询」页 | 新建只读列表页 | 中（多一个页面要维护） |

**推荐 A**：`KnowledgeView` 所有写操作都已按 `canWriteKb` 禁用，复用成本最低。

---

### 3.2 审核人员缺「待复核队列」——已在本地实现，待确认

**现象**：质量评审页此前只有统计看板，显示「待人工复核 3」但无具体任务列表。

**已做**（本地未推送）：在 `JudgeView` 增加「待复核队列」表格，
拉取 `state=NEED_HUMAN` 与 `state=DEGRADED` 的任务，含「去复核」入口。

**顺带澄清一处口径**：看板的「待人工复核」是**历史上被标记 needs_human 的评审记录数**（含已处理），
与队列的「当前待办任务数」不是同一个数。已在界面上分别标注，避免误读为「队列漏数据」。

**待你确认**：这个队列的字段（任务 / 状态 / 转复核原因 / 完成时间 / 操作）是否够用？
是否需要加「按专业筛选」或「指派给某人」？

---

### 3.3 `kb_manager` 角色不可用

**现象**：权限表与菜单规则都覆盖了它，但：

- 种子数据不创建该账号；
- 登录页不提供该身份；
- `test_role_matrix.py` 的菜单契约里也没有它。

**后果**：这是「文档里有、实际用不到」的角色，容易让接手的人困惑。

**建议**（二选一）

| 方案 | 做法 |
| --- | --- |
| **A. 让它可用** | 种子数据补建 `kb_manager` 账号 + 登录页身份卡片 + 菜单契约补一行 |
| B. 标注为预留 | 在权限表、手册、契约中明确写「预留角色，当前不分配」 |

**推荐 A**：规范维护在监理业务里是真实职责（谁负责把新规范入库？），
让它可用比标注预留更符合实际。

### 3.4 权限点语义重叠

| 权限点 | 当前用于 |
| --- | --- |
| `eval:review` | `POST /tasks/{id}/resume`（人工介入后继续）、`/eval/feedback`（建议改为它） |
| `judge:write` | `POST /reports/{id}/score`（触发 LLM 评审打分） |

两者由同一组角色（`expert` / `admin`）持有，但**分别绑在不同接口上**。
新增复核类接口时容易选错 —— 选错的后果是权限过松或过严。

**建议**：明确边界并写入文档：

- `eval:review` = 对**评估结论**的人工处置（确认、驳回、补充意见）
- `judge:write` = 触发**机器评审**这一动作本身

或直接合并为一个 `review:write`，减少选择成本。

## 4. P2：一致性与工程质量

### 4.1 CI 未构建镜像

CI 三个 job（后端测试 / 前端构建 / 编排校验）都通过，但**不构建 Docker 镜像**。
于是「CI 绿」不等于「镜像能跑」—— 本轮就出现过「Dockerfile 漏 COPY alembic 目录、容器反复重启而 CI 全绿」的情况。

**建议**：CI 增加一个 job，执行 `docker compose build`（不推送）。
这能在合并前抓住「镜像构建失败」「构建上下文缺失文件」这类问题。

---

### 4.2 无依赖漏洞扫描

`requirements.txt` 37 个依赖、前端含 60+ 包，CI 未做任何安全扫描。

**建议**：CI 增加

```yaml
- run: pip install pip-audit && pip-audit -r requirements.txt
- run: npm audit --audit-level=high
```

首次运行可能报出一批历史漏洞，建议先设为「仅报告不阻塞」，逐步清理后再改成阻塞。

---

### 4.3 迁移脚本命名缺序号对齐

现有三个迁移：`0001_baseline_schema` / `0002_knowledge_base_ownership` / `0003_agent_tool_call`。
命名规范，但**后续新增时必须手工保证序号递增**，容易撞号。

**建议**：在 `alembic/README` 中写明命名约定（`NNNN_简短描述.py`），
或改用 `alembic revision --autogenerate` 生成的时间戳前缀（默认行为，不会撞号）。

---

### 4.4 测试数据清理未自动化

本轮发现：审计脚本创建的临时账号会**留在库里污染用户列表**（用户列表一度从 4 行变 9 行）。
我补了 `cleanup_audit_users.py`（含 `--dry-run`），但需要人工记得执行。

**建议**：把清理挂到审计脚本的 `finally`，或让审计脚本用事务回滚（不落库）。
后者更彻底：审计只读场景下不该产生持久数据。

---

### 4.5 前端缺自动化测试

角色菜单这类「配置型逻辑」目前靠 Node 脚本 + E2E 截图校验，
没有前端单元测试（未安装 vitest —— 受限环境里 npm 落盘会被静默丢弃）。

**现状可接受**：`check-role-matrix.mjs` 已覆盖最关键的「前后端权限一致 + 菜单契约 + 落地页可达性」。
**建议**：待环境允许时补 vitest，至少覆盖 `permissions.ts` 与 `ROLE_HOME`。

## 附录 B：核实用法

```bash
# 1) 前端权限矩阵与各角色菜单契约（不需服务，最快）
node frontend/scripts/check-role-matrix.mjs

# 2) 逐角色实测后端权限边界（需服务）
docker compose exec api python scripts/audit_roles.py --base http://127.0.0.1:8000

# 3) 管理员两个管理模块的端点可用性
docker compose exec api python scripts/audit_admin_modules.py http://127.0.0.1:8000

# 4) 管理员界面实操核验（浏览器）
python backend/scripts/audit_admin_ui.py --base http://127.0.0.1:8080

# 5) 逐角色菜单截图（浏览器）
python backend/scripts/shot_roles.py --base http://127.0.0.1:8080

# 6) 清理审计产生的临时账号（先预览）
docker compose exec api python scripts/cleanup_audit_users.py --dry-run
```

> ⚠️ 审计脚本会创建临时账号（`audit_*`）用于逐角色实测，
> 结束后请执行第 6 条清理，否则会污染用户列表。

> ⚠️ 探测接口时必须带**合法参数**。用空 body 会拿到 422，
> 极易被误读为「无权限」—— 这是本轮踩过的坑，已写进 `audit_roles.py` 注释。
