## 示例场景

**地下室剪力墙混凝土浇筑质量评估**

材料里**故意埋了一个可被检出的问题**：混凝土入模温度实测 **35℃**，
超过 GB 50204-2015 第 5.3.3 条「不宜高于 30℃」的限值。
这样整条链路（发起 → Agent 分析 → 检出问题 → 转人工复核 → 裁定 → 签发）都能走通。

| 项 | 内容 |
| --- | --- |
| 评估类型 | 检验批质量评估 |
| 专业 | 结构工程 |
| 评估对象 | 地下室剪力墙（轴 3~7 / 标高 -6.20~-2.80） |
| 强度等级 | C35，方量 186 m³ |
| 提交材料 | 5 份（浇筑记录 / 配合比 / 原材料复验 / 试块强度 / 监理旁站） |
| 检索范围 | 默认全部知识库（4 部规范，94 个条款分块） |

## 步骤 2：执行评估

在任务详情页点右上角「**重新执行**」（首次为「执行评估」）。

**等待约 30 秒**，页面会显示五阶段执行轨迹：

```
规划(planning) → 检索(retrieval) → 条款匹配(clause_matching)
   → 分析(analysis) → 报告生成(report_generation)
```

**实测结果**（迭代 5 次）：

| 指标 | 值 |
| --- | --- |
| 任务状态 | `NEED_HUMAN`（转人工复核） |
| 总体结论 | **不符合**（`non_compliant`） |
| 风险等级 | **高** |
| 依据条款数 | 5 |
| 问题项数 | 6 |

> 因为总分低于阈值，系统**自动转入人工复核队列**（FR-JDG-05 低分拦截）。

## 步骤 3：查看评估报告

在「评估报告」面板可见**机器结论**与**人工裁定**两栏
（人工裁定此刻为「待复核」，签发状态为「未签发」）。

点开「质量评审」标签页可见 5 个维度的得分。

**条款匹配结果**（实测 6 条，摘要）：

| 条款 | 判定 | 风险 | 依据摘要 |
| --- | --- | --- | --- |
| **GB 50204-2015 5.3.3** | **不符合** | **高** | 入模温度实测 35℃，超「不宜高于 30℃」限值，且未采取降温措施 |
| GB 50204-2015 5.2.3 | 部分符合 | 中 | 外加剂含气量 3.1% 超 ≤3.0% 限值；缺检验批划分记录 |
| GB 50204-2015 5.2.3 | 证据不足 | 中 | 缺原材料进料批次划分记录与开盘鉴定记录 |
| GB 50204-2015 5.3.2 | 部分符合 | 中 | 旁站记录问题未形成书面整改闭环 |
| GB 50204-2015 5.3.5 | 部分符合 | 中 | 缺试块留置、养护及强度评定记录 |
| GB 50300-2013 3.0.7 | 部分符合 | 中 | 验收资料完整性不足 |

**报告结论（原文摘录）**：

> 主要问题为混凝土入模温度实测 35℃，超出 GB 50204-2015 第 5.3.3 条"不宜高于 30℃"的限值，
> 且未采取有效降温措施，监理仅口头要求整改，未形成书面闭环记录；外加剂含气量 3.1% 超出 ≤3.0% 限值……

**整改建议（原文摘录）**：

> 1. 立即对已浇筑部位进行温度监测与养护，必要时采取保温保湿措施，防止温度裂缝；
> 2. 后续混凝土浇筑前对罐车采取遮阳、喷淋降温等措施，控制入模温度不高于 30℃；
> 3. 补发书面监理通知单，要求施工单位提交书面整改回复及降温措施记录。

> 💡 **说明**：AI 不仅检出了我们埋设的入模温度问题，还额外发现了
> **外加剂含气量超标**（3.1% > 3.0%）——这是我编写示例时没有预设的。

## 步骤 4：审核人员人工复核

**退出登录** → 改用「**审核人员**」身份登录（自动进入「质量评审」页）

页面顶部是评审看板（评审次数、平均总分、待人工复核数、模型分歧、幻觉引用），
下方是「**待复核队列**」，可看到刚才那个任务。

### 两种复核路径

**路径 A：队列内直接裁定**（快捷）

在队列行内点「**判定合格**」或「**判定不合格**」。

**路径 B：进入详情裁定**（可逐条修订条款判定）

点「详情」进入任务详情页 → 在「人工裁定」栏点「**判定不合格**」。

### 本例建议选「判定不合格」

点「判定不合格」后，对话框要求：

| 字段 | 填写 |
| --- | --- |
| 裁定依据 | （**必填**）`混凝土入模温度 35℃ 超 GB 50204-2015 第 5.3.3 条限值，且监理未形成书面整改闭环；外加剂含气量超标。要求整改后重新报验。` |
| 处置方式 | 二选一，见下 |

**处置方式怎么选**：

| 选项 | 结果 | 适用 |
| --- | --- | --- |
| **驳回重跑** | 任务回到条款匹配阶段，带人工修订重新生成报告 | 补充材料后希望 AI 重新评估 |
| **直接落定不合格** | 任务终结，报告标记为不合格且**不予签发** | 问题已明确，重跑无意义 |

> ⚠️ **不填裁定依据无法提交** —— 前后端双重校验。这是质量责任的基本要求。

## 步骤 5：改判为合格并签发（演示改判能力）

监理现场常见「复核后发现遗漏」。已签发的报告**可以改判**，历次记录保留。

1. 先在「人工裁定」栏点「**判定合格**」
2. 填写：`已核对引用条款与整改回复，同意 AI 结论，予以签发`
3. 点「确认合格并签发」

**结果**：

| 项 | 变化 |
| --- | --- |
| 人工裁定 | 待复核 → **合格** |
| 状态徽标 | **已签发** |
| 是否签发 | 未签发 → **已签发生效** |
| 签认人 | `审核专家 · 2026-10-09 20:44:21` |
| 任务状态 | `NEED_HUMAN` → **已完成** |
| 机器结论 | **保持 `qualified` 不变**（不被人工覆盖） |

> 💡 **关键设计**：机器结论与人工裁定**并存**，互不覆盖。
> 「AI 判合格、人判不合格」这类分歧会记入模型迭代样本（FR-JDG-06）。

**若要演示改判**：在已签发状态下再点「判定不合格」，
系统会弹出二次确认「该报告此前已签发生效，改判将撤销签发」，
确认后签发被撤销，两条裁定记录都保留在库中。

| --- | --- |

| `rerun` | 是否驳回重跑 |

| `diverged` | **人工与机器是否分歧**（迭代样本标记） |

## 常见疑问

**Q1：执行后状态是 `NEED_HUMAN` 而不是 `COMPLETED`，是出错了吗？**
不是。这是**低分拦截**（FR-JDG-05）：总分低于阈值（默认 3.5）时自动转人工复核，
**不直接出具正式报告**。这正是本示例想要的效果。

**Q2：为什么「规范文档」卡片显示「仅你可见范围」？**
非管理员看到的是**自己权限范围内**的统计，与管理员看到的全局数字不同。
这是有意设计，避免出现「卡片有数字、列表是空的」的矛盾。

**Q3：工程师为什么看不到「质量评审」菜单？**
按角色职责分菜单：复核是审核人员的职责。工程师的菜单是
知识库 / 知识图谱 / 智能问答 / 评估任务。

**Q4：可以直接改报告里的结论吗？**
不能，也不应该。机器结论是 AI 质量的**原始证据**，用于模型迭代；
人工裁定是责任判定，记录在 `human_verdict` 等独立字段。
两者并列展示，界面会提示分歧。

**Q5：判定不合格后能改判吗？**
能。已签发的报告也可以改判，系统会二次确认并保留历次裁定记录。

**Q6：新手最快怎么看到效果？**
用仓库自带的示例任务（若已创建）：

```bash
# 在容器内创建示例任务（幂等，已存在则复用）
docker compose exec api python scripts/make_demo_task.py

# 执行评估（约 30 秒）
docker compose exec api python scripts/run_demo_eval.py <task_id>
```

然后按步骤 4–6 在界面上完成复核与签发。
清理示例数据：`docker compose exec api python scripts/make_demo_task.py --cleanup`
