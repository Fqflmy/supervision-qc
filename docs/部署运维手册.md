## 1. 环境要求

### 1.1 硬件建议

| 规模 | CPU | 内存 | 磁盘 | 说明 |
| --- | --- | --- | --- | --- |
| 试用 / 演示 | 2 核 | 4 GB | 20 GB | 使用硅基流动托管模型，无本地推理 |
| 小规模生产 | 4 核 | 8 GB | 50 GB | 建议并发 ≤ 5 个评估任务 |
| 中等规模 | 8 核 | 16 GB | 100 GB+ | 需把向量检索服务化后横向扩展 api |

> 关键约束：FAISS + BM25 索引**驻留 api 进程内存**，因此 `--workers 1`。
> 单实例内存占用实测约 400–700 MB（含 LangGraph 与检索索引）。

### 1.2 软件依赖

| 组件 | 版本要求 | 用途 |
| --- | --- | --- |
| Docker Engine | 24+ | 容器运行时（验证于 29.5.3） |
| Docker Compose | v2.20+ | 编排（验证于 v5.1.4） |
| （本机模式）Python | 3.11–3.12 | 验证于 3.12.13 |
| （本机模式）Node.js | 20+ | 验证于 v24.16.0 |

### 1.3 网络要求

对外需能访问（用于大模型调用）：

| 目标 | 用途 | 必需性 |
| --- | --- | --- |
| `api.deepseek.com` | 主 LLM（问答 / Agent / Judge） | 必需（或改用其他 OpenAI 兼容服务） |
| `api.siliconflow.cn` | Embedding + Reranker 托管服务 | 必需（或改用本地权重） |
| `dashscope.aliyuncs.com` | 备用 LLM（Qwen） | 可选 |

> 完全离线部署：把 BGE 权重放到 `backend/var/models/`，并把
> `EMBEDDING_PROVIDER` / `RERANKER_PROVIDER` 改为 `local`；
> LLM 需换成内网私有化模型（任何 OpenAI 兼容端点均可）。

## 2. 拓扑与端口

### 2.1 容器清单

| 服务 | 镜像 | 容器名 | 端口（宿主） | 健康检查 | 依赖 |
| --- | --- | --- | --- | --- | --- |
| `web` | 自建（Nginx） | `supervision-web` | **8080** | `/` 探活 | api healthy |
| `api` | 自建（Python） | `supervision-api` | 无（内部 8000） | `/api/v1/health` | postgres/redis/neo4j healthy |
| `postgres` | `postgres:16-alpine` | `supervision-postgres` | 无（内部 5432） | `pg_isready` | — |
| `neo4j` | `neo4j:5.20.0` | `supervision-neo4j` | 无（内部 7474/7687） | HTTP 7474 | — |
| `redis` | `redis:7-alpine` | `supervision-redis` | 无（内部 6379） | `redis-cli ping` | — |
| `minio` | `minio/minio:latest` | `supervision-minio` | 无（内部 9000/9001） | `mc ready local` | — |
| `prometheus` | `prom/prometheus:latest` | `supervision-prometheus` | 无（内部 9090） | — | — |
| `grafana` | `grafana/grafana:latest` | `supervision-grafana` | 无（内部 3000） | — | — |
| `embedding`※ | 自建（Python） | `supervision-embedding` | 无（内部 8510） | `/health` | 仅 `local-models` profile |
| `reranker`※ | 自建（Python） | `supervision-reranker` | 无（内部 8520） | `/health` | 仅 `local-models` profile |

※ 默认**不启动**（`profiles: ["local-models"]`），因为默认用硅基流动托管服务。

### 2.2 网络与卷

```
network: supervision (bridge)
volumes: pg_data · neo4j_data · neo4j_logs · redis_data · minio_data
         app_var（应用数据：索引/上传文件）· model_cache · prom_data · grafana_data
```

**只暴露 `web` 的 8080**。其余服务仅在容器网络内互通，这是刻意的安全设计：
业务入口只有 Nginx，`/api` 由 Nginx 反代到 api 容器。

### 2.3 本机开发模式（可选）

`deploy/docker-compose-infra.yml` 只起数据层，并把 **5432 / 7474 / 7687 / 6379** 映射到宿主，
供本机后端进程使用。它与全栈编排**不冲突**：

- 全栈用显式 `container_name: supervision-*`；
- infra 模式不写 `container_name`，由 Compose 按项目名命名（如 `supervision-infra-postgres-1`），
  且使用独立命名卷。

因此两种模式可在同一台机器共存；但**不要同时把两套 postgres 映射到宿主 5432**（infra 模式才映射）。

### 2.4 访问入口

| 地址 | 说明 | 账号 |
| --- | --- | --- |
| `http://<host>:8080` | 管理后台 | `admin / Admin@12345`（首次登录后请改） |
| `http://<host>:8080/api/v1/docs` | 接口文档（Swagger UI，经 Nginx 反代） | — |
| `http://<host>:8080/api/v1/health` | 健康检查（JSON） | 无需鉴权 |

## 3. 配置项全量说明

### 3.1 配置文件位置

| 模式 | 文件 | 说明 |
| --- | --- | --- |
| 全栈部署 | `deploy/.env` | 由 `deploy/.env.example` 复制；Compose 读取 |
| 本机开发 | `backend/.env` | 后端读取；前缀 `SUPERVISION_` |

**两个文件不要混用**：`backend/.env` 的变量会被 `app/config.py` 直接读取，
而 Compose 只认 `deploy/.env`。

> `.env` 必须保存为 **UTF-8 无 BOM**。带 BOM 时首行键名会解析失败，
> 表现为「填了 Key 却不生效」。

### 3.2 key 优先级

```
进程环境变量  >  deploy/.env（由 Compose 注入）  >  backend/.env  >  代码默认值
```

**最容易踩的坑**：调试时在命令行 `export`/`$env:` 设过某个变量，之后忘记清除，
它会一直覆盖 `.env`。例如残留 `SUPERVISION_EMBEDDING_PROVIDER=hash`
会让服务用哈希向量去查询真实 BGE 索引，检索分数直接跌到 0.002 量级。

自查命令：

```bash
docker compose exec api env | grep SUPERVISION_ | sort
```

## 4. 启动与停止

### 4.1 全容器启动（推荐）

```bash
cd <项目根目录>
docker compose up -d
```

一条命令完成：启动数据层 → 构建并启动 api 与 web → api 容器入口自动完成
**幂等数据初始化**（写示例规范 + 建向量索引）→ 服务就绪。

首次启动约 1–3 分钟。观察进度：

```bash
docker compose logs -f api          # 看到 [entrypoint] 初始化完成 即就绪
docker compose ps                   # 所有服务应为 healthy / running
```

预期输出（片段）：

```
[entrypoint] 后端容器启动
[entrypoint] 等待数据库就绪…
[entrypoint] 数据库就绪
[entrypoint] 初始化示例数据与向量索引（幂等，已有数据会跳过）…
[OK] GB 50204-2015 入库：chunks=29 pages=0 namespace=kb_1 degraded_embedding=False
...
[DONE] 本次写入 4 份规范
[entrypoint] 初始化完成
[entrypoint] 启动 API 服务：uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

再次启动时因数据已存在，会输出 `[DONE] 本次写入 0 份规范` 并快速跳过。

### 4.2 使用启动脚本

```powershell
.\start.ps1                       # 环境自检 + 准备 .env + 启动 + 等待健康 + 汇总地址
.\start.ps1 -ApiKey sk-xxxxxxxx   # 顺手写入 DeepSeek Key
.\start.ps1 -Build                # 强制重建镜像
.\start.ps1 -Offline              # 离线演示（LLM_PROVIDER=fake）
.\start.ps1 -NoWait               # 不等待健康检查
.\start.ps1 -Down                 # 停止
```

> PowerShell 默认执行策略可能禁止运行 `.ps1`。**双击 `start.bat`** 即可
> （内部使用 `-ExecutionPolicy Bypass`，只对本次调用生效，不改系统策略）。

### 4.3 停止与重置

```bash
docker compose stop                 # 停止（容器保留，数据保留）
docker compose down                 # 停止并删除容器（数据卷保留）
docker compose down -v              # 停止并删除容器 + 数据卷（彻底重置，慎重）
docker compose restart api          # 只重启后端
docker compose up -d --build api    # 改代码后重建并更新后端
```

### 4.4 灰度/回滚思路

本系统无内置版本路由，回滚依赖镜像标签：

```bash
docker tag supervision-qc-api:latest supervision-qc-api:2026.08
# 升级
docker compose up -d --build api
# 回滚
docker tag supervision-qc-api:2026.08 supervision-qc-api:latest
docker compose up -d --force-recreate api
```

> **数据库结构变更需自行迁移**：`init_db()` 只做 `create_all`（建缺失表），不做列变更。
> 升级前后请先备份 `pg_data`。

### 4.5 离线演示模式

无任何模型 Key 时仍可验证全链路：

```powershell
.\start.ps1 -Offline
```

此时 `LLM_PROVIDER=fake`，使用确定性 Fake 网关；检索降级为哈希向量。
用于链路验证与界面演示，**不代表真实推理质量**。

## 5. 数据管理与备份恢复

### 5.1 数据分布

| 数据 | 位置（容器） | 位置（宿主卷） | 说明 |
| --- | --- | --- | --- |
| 业务库 | `/var/lib/postgresql/data` | `supervision-qc_pg_data` | 18 张表：文档/条款/任务/报告/评审/审计 |
| 图谱 | `/data` | `supervision-qc_neo4j_data` | 节点与关系 |
| 缓存 | `/data` | `supervision-qc_redis_data` | 可丢 |
| 原始文件 | `/data` | `supervision-qc_minio_data` | 仅 `STORAGE_BACKEND=minio` 时 |
| **向量索引 + 上传文件** | `/app/var` | `supervision-qc_app_var` | **FAISS/BM25 索引、本地存储文件、日志** |

> 索引可重建，业务库不可重建，因此**备份优先级：`pg_data` > `neo4j_data` > `app_var`**。

### 5.2 备份

```bash
# 1) 业务库（逻辑备份，推荐跨版本迁移用）
docker compose exec -T postgres pg_dump -U supervision -d supervision \
    --clean --if-exists > backup_$(date +%Y%m%d).sql

# 2) 图谱（逻辑备份，需 apoc 插件，已内置）
docker compose exec -T neo4j cypher-shell -u neo4j -p supervision123 \
    "CALL apoc.export.cypher.all(null,{stream:true})" > graph_$(date +%Y%m%d).cypher

# 3) 应用数据卷（索引与上传文件）
docker run --rm -v supervision-qc_app_var:/data -v "$PWD":/backup alpine \
    tar czf /backup/app_var_$(date +%Y%m%d).tar.gz -C /data .
```

### 5.3 恢复

```bash
# 停应用，保留数据层
docker compose stop api web

# 恢复业务库
docker compose exec -T postgres psql -U supervision -d supervision < backup_20260801.sql

# 恢复应用数据卷
docker run --rm -v supervision-qc_app_var:/data -v "$PWD":/backup alpine \
    sh -c "rm -rf /data/* && tar xzf /backup/app_var_20260801.tar.gz -C /data"

# 起应用
docker compose start api web
```

### 5.4 索引重建

以下情况需要重建索引（FAISS + BM25）：

- 更换 Embedding 模型或维度；
- 索引文件损坏；
- 手工批量修改了条款内容；
- 升级引入了新的切分规则。

```bash
docker compose exec api python scripts/rebuild_index.py
docker compose exec api python scripts/rebuild_index.py --batch-size 32   # 调整批次
```

实测：94 个分块约 16 秒（硅基流动 Embedding 约 6.5 条/秒）。

> **务必保证建索引与查询使用同一个 Embedding 模型**。二者不一致时不会报错，
> 但检索质量会崩坏（表现为分数极低、`no_evidence=true`），属于最隐蔽的故障之一。

### 5.5 完全重置

```bash
docker compose down -v
docker compose up -d
```

数据卷被删除后，api 容器入口会自动重新初始化示例数据与索引。

### 5.6 数据库结构迁移（Alembic）

**为什么必须有迁移机制**：项目早期用 `Base.metadata.create_all()` 建表，
它**只创建缺失的表，不处理列变更**——加字段、改类型、改索引都不会生效，
且没有回滚手段。因此正式环境的表结构变更必须走 Alembic 迁移。

#### 工作方式

表结构管理方式由 `SUPERVISION_DB_SCHEMA_MODE` 决定：

| 取值 | 行为 | 适用 |
| --- | --- | --- |
| `auto`（默认） | `environment=production` 用 alembic，其他环境用 create_all | 通用 |
| `alembic` | 强制走迁移（启动时自动 `upgrade head`） | 正式环境 |
| `create_all` | 强制用 create_all | 仅临时验证，会绕过版本管理 |

开发环境刻意保留 `create_all`，避免每改一次模型就要生成迁移；
**正式环境必须用 `alembic`**，否则结构变更会静默失效。

#### 常用命令

```bash
cd backend

python -m alembic current                        # 当前版本
python -m alembic history --verbose              # 迁移历史
python -m alembic upgrade head                   # 升级到最新
python -m alembic downgrade -1                   # 回退一步
python -m alembic upgrade head --sql             # 只输出 SQL，不执行（供 DBA 审核）
python -m alembic revision --autogenerate -m "描述"   # 依据模型变更生成迁移
```

容器内执行：

```bash
docker compose exec api python -m alembic current
docker compose exec api python -m alembic upgrade head
```

#### 新增字段的标准流程

```bash
# 1) 修改 app/db/models.py
# 2) 生成迁移（会自动对比模型与库的差异）
cd backend && python -m alembic revision --autogenerate -m "add xx column to yy table"
# 3) 人工审查生成的迁移（autogenerate 可能漏掉重命名、默认值等）
# 4) 在副本库上演练
python -m alembic upgrade head
# 5) 随代码一起提交，上线时由启动流程自动应用
```

> ⚠️ **autogenerate 不是万能的**：列重命名会被识别成「删一列 + 加一列」导致数据丢失；
> 索引与约束的变更也可能漏检。生成后**必须人工审查**。

#### 存量库纳管（重要）

若数据库此前由 `create_all` 建立，**不要执行基线迁移**（会因表已存在而报错），
应直接标记为已应用：

```bash
docker compose exec api python -m alembic stamp head
```

判断是否需要 stamp：

```bash
docker compose exec api python -c "
import sys; sys.path.insert(0,'/app')
from app.db.session import alembic_has_version
print('已纳入版本管理:', alembic_has_version())"
```

输出 `False` 且业务表已存在 → 执行 `alembic stamp head`。

#### 回滚

```bash
python -m alembic downgrade -1        # 回退一步
python -m alembic downgrade base      # 回退全部（清空业务表，谨慎）
```

**上线前务必在副本库演练回滚**，并确认 `downgrade()` 里确实写了回退逻辑
（基线迁移的 `downgrade` 会删除所有业务表）。

#### 迁移文件位置与校验

| 路径 | 说明 |
| --- | --- |
| `backend/alembic/env.py` | 从应用配置读连接串（不把密码写进 ini） |
| `backend/alembic/versions/*.py` | 迁移脚本，**必须提交到版本库** |
| `backend/scripts/gen_baseline_migration.py` | 离线生成基线迁移（不需要连库） |

## 7. 故障排查手册

> 每一条都来自实际发生并已修复的问题，含根因与修法。

### 7.1 接口全部卡住，Agent 一直不返回

**现象**：检索/问答/Agent 请求长时间无响应；`pg_stat_activity` 中出现多条
`CREATE INDEX CONCURRENTLY IF NOT EXISTS checkpoints_thread_id_idx`，
且一直停在 `Lock/virtualxid` 或 `Lock/relation`。

**根因**：`AsyncPostgresSaver.setup()` 会执行 `CREATE INDEX CONCURRENTLY`。
该语句**不能回滚、且必须等待所有并发事务结束**。当另有连接停在
`idle in transaction`（例如持有会话执行了数十秒的 LLM 调用）时，两者互等形成死锁；
后续重试连接不断堆积，最终整个服务瘫痪。

**确认**：

```bash
docker compose exec postgres psql -U supervision -d supervision -c "
SELECT pid, state, wait_event_type, wait_event, now()-xact_start AS age,
       left(regexp_replace(coalesce(query,''),'\s+',' ','g'),60) AS q
FROM pg_stat_activity WHERE datname='supervision' AND (state='idle in transaction' OR wait_event_type='Lock');"

docker compose exec postgres psql -U supervision -d supervision -c "
SELECT c.relname, i.indisvalid FROM pg_class c JOIN pg_index i ON i.indexrelid=c.oid
WHERE c.relname LIKE 'checkpoint%';"
```

`indisvalid = f` 表示索引处于**无效**状态（并发建索引被中断）。

**修复**：

```bash
docker compose exec -T api python /app/scripts/fix_checkpoint_locks.py          # 只诊断
docker compose exec -T api python /app/scripts/fix_checkpoint_locks.py --fix    # 终止卡死会话并重建索引
```

**已实施的根治措施**（升级后不会再发生）：

1. 检查点构建前先探测 `checkpoint_migrations`，迁移已就绪则**跳过 `setup()`**，
   从根上避免重复执行 `CREATE INDEX CONCURRENTLY`；
2. `setup()` 加 180 秒超时兜底，绝不允许无限挂起；
3. `GraphStore` 的连通性探测使用**可重入锁 + 非阻塞抢占**，Neo4j 不可达时不会拖死健康检查。

> ⚠️ **不要再通过设置 `idle_in_transaction_session_timeout` 来"防长事务"**。
> 曾用 60 秒阈值试图自动回收空闲事务，结果误杀长任务的正常连接，
> 引发 [7.2](#72-长任务执行中连接被回收落库失败) 所述故障，该做法已被移除。
> 检查点连接是 autocommit 短事务，本就不会长期 idle。

### 7.2 长任务执行中连接被回收，落库失败

**现象**：Agent 评估任务执行到后半段失败，日志出现

```
sqlalchemy.exc.PendingRollbackError:
Can't reconnect until invalid transaction is rolled back.
Please rollback() fully before proceeding
```

任务在页面上显示为仍在执行或 `PENDING`，但接口曾返回执行成功——**状态没有真正落库**。

**根因**：Agent 一次评估会持续数十秒到数分钟（多次 LLM 调用），而请求会话在这段时间里
一直持有数据库连接。该连接可能被服务端回收：

- 连接级 `idle_in_transaction_session_timeout` 到期（数据库主动断开）；
- 连接池回收、网络抖动、数据库重启。

连接被回收后，SQLAlchemy 会把事务标记为「失效」，此后任何 SQL 都抛
`PendingRollbackError`。PostgreSQL 日志会留下直接证据：

```
FATAL: terminating connection due to idle-in-transaction timeout
```

**确认**：

```bash
# 1) 应用日志中是否有该异常与"落库时会话连接已失效"的告警
docker compose logs api | grep -E "PendingRollback|连接已失效"

# 2) PostgreSQL 侧是否记录过强制断开
docker compose logs postgres | grep "idle-in-transaction timeout"

# 3) 当前生效的空闲事务阈值（不应过小）
docker compose exec postgres psql -U supervision -d supervision \
  -c "SHOW idle_in_transaction_session_timeout;"
```

**修复（代码已内置自愈，无需人工干预）**

`run_evaluation` 的落库阶段会捕获这类异常并重试一次。**恢复动作的顺序至关重要**：

```python
session.invalidate()   # ① 必须先丢弃已死的连接
session.rollback()     # ② 再复位事务状态
_apply_task_fields()   # ③ 重放任务字段（rollback 会使 ORM 对象过期）
_write_results()       # ④ 重放结果落库
```

顺序颠倒会**适得其反**——这也是本案例最反直觉的地方：

| 恢复动作 | 实测结果 |
| --- | --- |
| `invalidate()` | **3/3 成功** |
| `invalidate()` + `rollback()` | **3/3 成功** |
| `rollback()` + `invalidate()` | **0/3 失败** |
| `close()` + `invalidate()` | **0/3 失败** |

原因：`rollback()` / `close()` 都会在**已死的连接上再发一次 `ROLLBACK` 命令**，
psycopg 直接报 `AdminShutdown`，反而阻断了恢复路径；只有先 `invalidate()`
才能真正丢弃坏连接。

重放是安全的：落库函数是「先删后插」的幂等写法，且此刻事务尚未提交，
因此不会产生重复数据。

> **反面教材（已回退的方案）**：曾在落库前调用 `session.close()` 想"换个连接"。
> 但 `close()` 会让 `task` 对象脱离会话，导致状态**写不进库**——
> 接口返回 `COMPLETED`，数据库里仍是 `PENDING`。该方案已废弃。

**回归测试**：`backend/tests/test_db_resilience.py`（5 项）覆盖了正向恢复与
反向顺序，其中「先 `rollback()` 必失败」一条专门用来锁住顺序，防止后人调换。

**预防性配置**

| 配置 | 建议值 | 说明 |
| --- | --- | --- |
| `SUPERVISION_DB_IDLE_TRANSACTION_TIMEOUT_SECONDS` | `900`（15 分钟） | 仅作兜底；正常任务碰不到，真正卡死的事务仍会被回收。**不要设成几十秒** |
| 检查点连接池超时 | 不设置 | 检查点是 autocommit 短事务；设阈值只会误杀长任务连接，并可能让 Agent 中途降级为内存检查点 |

### 7.4 容器里数据明明写入了却检索不到

**根因**：卷挂载点与应用读取路径不一致。曾出现卷挂在 `/app/../var`，
而应用读 `/app/var`，索引被写进容器可写层——重启即丢失，
且初始化容器与 api 容器各写各的副本。

**确认**：

```bash
docker compose exec api python -c \
  "from app.config import settings; print(settings.data_dir, settings.faiss_index_dir)"
docker compose exec api ls -la /app/var/faiss/
docker inspect supervision-api --format '{{range .Mounts}}{{.Destination}} <- {{.Name}}{{"\n"}}{{end}}'
```

要求：`settings.faiss_index_dir` 必须落在挂载卷的目标路径下（`/app/var/faiss`）。

**处置**：确认 `deploy/docker-compose.yml` 中
`SUPERVISION_DATA_DIR: /app/var` 与 `- app_var:/app/var` 同时存在且一致。

### 7.9 前端页面空白 / 接口 404

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 页面 200 但白屏 | 静态资源未构建或缓存 | `docker compose up -d --build web`，硬刷新（Ctrl+F5） |
| 接口 404 | Nginx 反代路径配置 | 确认访问 `/api/v1/...` 而非 `/api/...`（以实际路由为准） |
| 接口 502 | api 未就绪 | `docker compose logs api`，等 `或查看 ps` healthy |
| 接口 504 | Nginx 读超时（默认 600s） | 单次请求超过 10 分钟；检查 Agent 是否卡住（见 7.1） |
| CORS 报错 | 来源不在白名单 | compose 中 `SUPERVISION_CORS_ORIGINS` 追加实际域名 |

> `SUPERVISION_CORS_ORIGINS` 支持**逗号分隔**（如 `http://a,http://b`），
> 也兼容 JSON 数组写法。

### 7.10 磁盘增长过快

主要来源与处置：

| 来源 | 处置 |
| --- | --- |
| `llm_call_log` / `audit_log` 表 | 定期归档：`DELETE FROM llm_call_log WHERE created_at < now() - interval '90 days';` |
| Docker 日志 | `docker compose logs` 有上限；宿主 `/var/lib/docker` 可 `docker system prune` |
| Neo4j 日志卷 | `neo4j_logs` 定期清理 |
| 上传的原始文件 | `app_var` 卷；按业务策略清理 |
| 旧镜像 | `docker image prune -a`（注意会清掉回滚标签） |

### 7.11 PowerShell 脚本报「未对文件进行数字签名」

**原因**：执行策略为 `RemoteSigned`，本地未签名脚本被拒。

**处置**：双击对应 `.bat` 包装器，或

```powershell
powershell -ExecutionPolicy Bypass -File .\start.ps1
```

不要修改系统全局执行策略。另注意 `.ps1` 若保存为 **UTF-8 无 BOM**，
Windows PowerShell 5.1 会按 ANSI 解析中文，导致语法错误；本仓库脚本均为 UTF-8 **带 BOM** + CRLF。

## 9. 安全加固

### 9.1 必改项（上线前）

```dotenv
# deploy/.env
SUPERVISION_ENVIRONMENT=production          # 开启强制安全校验
JWT_SECRET=<32 位以上随机串>                 # 不设置则服务拒绝启动
POSTGRES_PASSWORD=<强密码>
NEO4J_PASSWORD=<强密码>
MINIO_SECRET_KEY=<强密码>
GRAFANA_PASSWORD=<强密码>
# 默认管理员账号：上线前关闭自动写入并改掉默认密码
SEED_DEFAULT_ADMIN=false
SEED_DEFAULT_ADMIN_PASSWORD=<强密码>
```

生成随机串：`python -c "import secrets;print(secrets.token_urlsafe(48))"`

**关于 JWT 密钥的强制校验（默认安全）**

`JWT_SECRET` 曾以占位值 `please-change-this-secret-in-production` 随公开仓库分发，
这意味着**任何拿到仓库的人都能伪造令牌、绕过鉴权**。现已改为：

| 环境 | 行为 |
| --- | --- |
| `SUPERVISION_ENVIRONMENT=production` | 密钥为空、占位值、或长度 < 32 → **拒绝启动**并打印修复方法 |
| 其他（默认 `dev`） | 自动生成随机密钥并告警，保证开箱即用 |

配置模板中的 `JWT_SECRET` 已默认留空，不再分发占位值；回归测试
`backend/tests/test_security_policy.py`（11 项）会校验模板与校验逻辑，
防止占位密钥再次进入仓库。

**其他安全提示（非生产环境仅告警，不阻断）**

启动日志中会打印 `安全提示`，覆盖：未启用刷新令牌、访问令牌有效期过长、
默认管理员密码未修改、未强制首次登录改密。这些项在生产环境应逐条确认。

### 9.2 网络暴露

- 只暴露 **8080**。不要为图省事把 5432/7687/8000 映射到公网；
- 前置反向代理（Nginx/Traefik）并启用 HTTPS；
- 生产建议把 `api` 与数据层放在同一内网，管理后台限制来源 IP。

### 9.3 数据与密钥

- `deploy/.env` 与 `backend/.env` 均**不要提交到版本库**（已在 `.gitignore`）；
- 密钥通过环境变量或密钥管理服务注入，避免固化在镜像里；
- 对外调用使用 HTTPS（当前默认端点均为 HTTPS）。

### 9.4 应用层

- JWT 含访问令牌与刷新令牌，密码使用 bcrypt 存储（含 72 字节截断处理）；
- 上传文件按扩展名白名单校验（`SUPERVISION_UPLOAD_ALLOWED_EXT`）；
- 所有关键操作写审计日志，可追溯；
- Judge 具备幻觉引用识别（引用不存在的条款会扣分），避免报告编造依据。

### 9.5 审计与合规

`audit_log` 表记录：动作、操作人、对象、结果、IP、User-Agent、时间、明细。
建议定期导出归档并设置保留期（见 7.9）。
