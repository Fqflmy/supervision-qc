# 术语规范

> 本文件是**强制口径**。新增界面文案、接口字段、测试断言前请先查阅，
> 避免再次引入「同一个词指两个对象」的歧义。

---

## 一、为什么需要这份规范

**真实事故**：报告中显示「复核结论：合格」，用户无法判断这是
「AI 报告的结果合格」还是「评估项目本身合格」。

根因不是文案不好，而是**数据模型的语义缺失**：系统里有两个**不同对象**的判定，
却共用了「合格/不合格」一个词，且标签里完全没有出现「报告」二字。

**规律**：只要一个结论**没有显式标注对象**，用户就一定会误读。
因此本规范的核心是——**每个结论必须能回答「在判定什么」**。

---

## 二、三层结论（唯一口径）

报告中涉及三个不同层次，**对象各不相同**：

| 层次 | 统一名称 | 判定对象 | 判定人 | 取值 | 显示标签 |
| :-: | --- | --- | --- | --- | --- |
| L1 | **评估结论** | **工程质量**（实体/检验批符合性） | AI | `Verdict` | 符合 / 不符合 / 部分符合 / 不适用 / 证据不足 |
| L2 | **报告复核决定** | **AI 报告**（能否对外出具） | 人工 | `HumanVerdict` | **接受报告** / **退回报告** |
| L3 | **报告签发状态** | 报告能否作为正式依据 | 人工 | `is_final` | **已签发** / **未签发** |

> L2 与 L3 是**同一次复核动作的两个侧面**：接受报告 → 签发；退回报告 → 不签发。
> 界面合并为一个「报告复核决定」区块，但签发后果必须写明
> （「可作为正式依据」/「不得作为正式依据」）。

### SRS 依据

SRS 第 92 行：质量评估专家的职责是「复核**评估结论**、修订评分、**终审签发**」。
→ **复核对象是报告与其中的评估结论，不是工程实体。**

## 三、术语对照表（禁止使用左列）

| ❌ 禁止 | ✅ 必须使用 | 原因 |
| --- | --- | --- |
| 复核结论：合格 | 复核决定：接受报告 | 「结论+合格」双重点向工程质量 |
| 复核结论：不合格 | 复核决定：退回报告 | 同上 |
| 判定合格 | 接受并签发 | 动作词天然绑定对象 |
| 判定不合格 | 退回报告 | 同上 |
| 直接落定不合格 | 直接结束（报告不予签发） | 明确后果，避免指向质量 |
| 已复核不合格 | 已退回 | 区分「报告被退回」与「工程不合格」 |
| 裁定 | 复核（作为动作名） | SRS 用「复核/签发」 |
| 裁定依据 | 复核意见 | 同上 |
| 签认人 | 复核人（签发场景）/ 签认署名（身份字段） | 区分「人」与「署名」 |
| 是否签发 | 签发状态 | 名词化，便于加后果说明 |
| 机器结论 | 评估结论（AI 判工程质量） | 「机器结论」不说判什么 |
| 总体结论 | 评估结论 | 同上 |
| 复核（单独作列名） | 报告复核（人工判报告） | 必须点明对象 |
| Judge 总分 / 等级 | Judge 总分（评报告质量） | 评的是**报告质量**，不是工程 |

### 两个易混维度

| 维度 | 评什么 | 由谁评 | 取值示例 |
| --- | --- | --- | --- |
| **评估结论** | 工程质量 | AI | 符合 / 不符合 |
| **Judge 评分** | **报告质量**（引用准确性、结论合理性…） | LLM-as-Judge | 3.88 / 5.00，等级「合格」 |

> Judge 等级里的「合格」评的是**报告**，与工程质量无关。
> 界面必须写明「评报告质量」，否则同样会被误读。

## 四、强制规则

### 规则 1：禁止裸露的结论词

不许单独出现「合格 / 不合格 / 通过 / 未通过」。
必须满足其一：
- 带对象（「报告复核」「评估结论」）；
- 用**动作词**（「接受报告」「退回报告」）；
- 带后果说明（「不得作为正式依据」）。

### 规则 2：动作词优先于状态词

| 状态词 | 动作词 | 误读风险 |
| --- | --- | --- |
| 复核合格 | 接受报告 | 高 → 无 |
| 复核不合格 | 退回报告 | 高 → 无 |

「接受报告」不可能被误读成「工程合格」；「复核合格」一定会。

### 规则 3：两个判定必须成对出现

任何展示人工复核决定的地方（列表、详情、队列），
**同一屏内必须能看到评估结论**。否则「退回报告」会被误读为「工程不合格」。

### 规则 4：未复核 ≠ 已退回

`human_verdict` 为 `None` 时显示「待复核 / 尚未复核」，
**不得**默认成「接受」或「退回」。派生函数在无值时返回 `None`。

### 规则 5：解释「为何可以 不符合 + 接受报告」

这是最容易被当成 bug 的组合。界面必须有一句说明：

> 两者判定对象不同，结论可并存、不矛盾

### 数据库字段（不改）

| 字段 | 值 | 说明 |
| --- | --- | --- |
| `eval_report.overall_verdict` | Verdict / JudgeGrade | 工程质量结论（AI） |
| `eval_report.human_verdict` | `qualified` / `unqualified` | **历史字段**，语义 = 接受/退回报告 |
| `eval_report.is_final` | bool | 是否签发 |
| `eval_report.review_comment` | text | 复核意见 |

> **刻意不做字段重命名**：收益低、破坏性大（历史数据、SRS 引用、既有测试全需改）。
> 显示层映射即可解决用户困惑。
