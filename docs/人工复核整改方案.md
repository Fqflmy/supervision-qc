## 1. 问题定性

### 1.1 现状：有「修订」没有「裁定」

当前人工复核能做的事：

| 能力 | 现状 |
| --- | --- |
| 进入复核 | ✅ 低分/分歧/幻觉引用时置 `NEED_HUMAN` |
| 修订单条条款判定 | ✅ 复核对话框里逐条改 `compliant` / 其它 |
| 写复核说明 | ✅ 存入 `human_feedback.comment` |
| **给出合格 / 不合格结论** | ❌ **没有** |
| **终审签发报告** | ❌ **没有**（`is_final` 永远是 `false`） |

两条路径（`/resume` 的 `continue` 与 `cancel`）都只是「让 Agent 继续跑」或「终止任务」，
**没有一个动作代表「我作为复核人，判定这份结论合格/不合格」**。

### 1.2 取证

```
app/db/models.py:438-440
    reviewed_by:  ...   ← 定义了，但全仓库无写入点
    reviewed_at:  ...   ← 定义了，但全仓库无写入点
    is_final:     ...   ← 定义了，仅被 eval.py:397 读取，无写入点

frontend/src/views/EvalDetailView.vue
    「人工复核」对话框 = 复核说明 + 逐条修订判定 + [终止任务 | 提交并重新执行]
    → 无「合格 / 不合格」按钮，也无「签发」相关界面
```

`FeedbackCreate.action` 是**自由字符串**（`max_length=32`，无枚举约束），
没有合格/不合格语义 —— 即使写了 `action="unqualified"`，也没有任何逻辑会读它。

### 1.3 对照 SRS：这是需求缺口，不是「锦上添花」

| SRS 出处 | 原文 | 实现现状 |
| --- | --- | --- |
| 角色定义（第 92 行） | 质量评估专家职责：复核与裁定、修订评分、**终审签发** | ❌ 无裁定、无签发 |
| 业务流程（第 142 行） | 专家复核**签发** → 报告归档 → 全链路留痕 | ❌ 签发环节缺失；报告无「已签发」概念 |
| FR-AGT-11（P1） | 关键节点（条款匹配确认、**报告签发**）支持人工介入与修改后继续执行 | ⚠️ 只实现了「继续执行」，未实现「签发」 |
| FR-JDG-05（P0） | 低分报告 100% 进入复核队列，**不直接出具正式报告** | ⚠️ 有队列，但**「正式报告」与「草稿」无法区分** |
| FR-JDG-06（P1） | 专家复核结果回写为训练样本 | ⚠️ 只回写了逐条修订，未回写最终结论 |

**结论**：`is_final` 字段的存在说明原设计意图里**本来就有「签发」概念**，
只是实现时漏掉了。这不是新增需求，而是补齐需求。

### 1.4 一个真实的风控后果

`STATE_TRANSITIONS` 中 `JUDGING → COMPLETED` 是允许的，即
**评分达标的报告无需任何人工动作即可进入 `COMPLETED`**。
配合「没有签发概念」，结果是：

> 报告一旦生成就等同于「正式出具」，**没有任何环节能表达「这份结论尚未经人确认」**。

对监理这种强合规场景，这比「界面少两个按钮」严重得多 ——
无法回答「这份报告是谁签认的、结论是什么」。

## 2. 目标与验收标准

### 2.1 整改目标

给人工复核补上**明确的裁定动作**：复核人必须显式给出「合格」或「不合格」，
并留下结论、依据、签认人与时间；报告只有在**判定合格（或降级后合格）**时才成为「正式报告」。

### 2.2 验收标准

| # | 标准 | 验证方式 |
| --- | --- | --- |
| 1 | 复核人在界面上能点「判定合格」与「判定不合格」 | 浏览器实测 |
| 2 | 判定后报告记录 `human_verdict` / `reviewed_by` / `reviewed_at` / `is_final` | 查库 + 接口返回 |
| 3 | 判定合格 → 报告 `is_final=true`，任务进入 `COMPLETED`，可导出为正式报告 | 接口 + 导出 |
| 4 | 判定不合格 → 任务回到 `MATCHING` 重跑，或标记「已复核不合格」并终止 | 状态机 + 留痕 |
| 5 | 非复核角色（engineer / viewer）调用判定接口返回 403 | 越权回归测试 |
| 6 | 每次判定写入 `human_feedback` 与 `audit_log`，可追溯 | 审计查询 |
| 7 | 判定与机器结论不一致时，报告同时保留**机器结论**与**人工结论** | 字段核对 |
| 8 | 未签发（`is_final=false`）的报告在导出/列表中有明确标识 | 界面核验 |

## 3. 方案设计

### 3.1 数据模型：区分「机器结论」与「人工裁定」

**关键原则：不覆盖机器结论。** 机器结论是 AI 质量的原始证据（用于 FR-JDG-06 反馈闭环
与模型迭代），人工裁定是责任判定 —— 两者必须并存，否则失去对比价值。

`eval_report` 现有字段与拟新增字段：

| 字段 | 归属 | 现状 | 说明 |
| --- | --- | --- | --- |
| `overall_verdict` | **机器** | ✅ 已有 | AI 生成的总体结论 |
| `risk_level` | 机器 | ✅ 已有 | 风险等级 |
| `human_verdict` | **人工** | 🆕 新增 | `qualified` / `unqualified`，**新增后即为「人工结论」唯一来源** |
| `review_comment` | 人工 | 🆕 新增 | 裁定依据/说明（与逐条修订说明分开） |
| `reviewed_by` | 人工 | ⚠️ 已有未用 | 签认人 `user_id` |
| `reviewed_at` | 人工 | ⚠️ 已有未用 | 签认时间 |
| `is_final` | 人工 | ⚠️ 已有未用 | 是否已签发生效 |

> 为什么另加 `human_verdict` 而不是复用 `overall_verdict`：
> 复用会让「AI 原始结论」被人工覆盖且不可恢复，等于丢掉 FR-JDG-06 所需的对比样本，
> 也无法回答「AI 判合格、人判不合格」这类关键分歧。

### 3.2 枚举与状态语义

```python
class HumanVerdict(StrEnum):
    """人工复核裁定（终审结论）。"""
    QUALIFIED = "qualified"      # 合格：可签发为正式报告
    UNQUALIFIED = "unqualified"  # 不合格：不予签发

class ReviewStatus(StrEnum):
    """报告的复核状态（派生展示用）。"""
    PENDING = "pending"          # 待复核（NEED_HUMAN / DEGRADED 且无人工结论）
    QUALIFIED = "qualified"      # 已复核合格（is_final=True）
    UNQUALIFIED = "unqualified"  # 已复核不合格
```

**状态流转**（在现有 `STATE_TRANSITIONS` 内，无需新增状态）：

```
NEED_HUMAN ──判定合格──→ COMPLETED   （报告 is_final=True，正式出具）
           ──判定不合格→ MATCHING    （带裁定意见重跑；不覆盖机器结论）
           ──无法定论──→ CANCELLED   （现有「终止任务」）
DEGRADED   ──人工介入──→ NEED_HUMAN  （现有路径，再走上表）
```

**「不合格」的两种处理**（需业务确认，见 §7）：

| 做法 | 效果 | 建议 |
| --- | --- | --- |
| **A. 驳回重跑** | 任务回 `MATCHING`，带人工修订重新生成报告 | ✅ 推荐为默认 |
| B. 直接落定「不合格」 | 任务进 `COMPLETED`，但 `human_verdict=unqualified`、`is_final=False` | 作为「重跑也无意义」时的选项 |

> 二者都需要：有些问题（如材料确实不足）重跑无意义，应当允许直接落定不合格并留痕。
> 因此接口设计为一个 `decision` 参数带 `rerun` 开关。

### 3.3 接口设计

| 接口 | 方法 | 权限 | 说明 |
| --- | --- | --- | --- |
| `/eval/tasks/{id}/review` | `POST` | `eval:review` | **提交人工裁定**（合格 / 不合格） |
| `/eval/tasks/{id}/review` | `GET` | `eval:read` | 查询裁定状态与历史 |
| `/eval/reviews/pending` | `GET` | `eval:review` | 待复核队列（后端分页版，替代前端筛状态） |

**请求体**（`POST`）：

```json
{
  "verdict": "unqualified",
  "comment": "第 3 条引用条款为已废止版本，且缺少材料进场复验记录，不予签发",
  "rerun": true,
  "match_revisions": [
    { "match_id": 12, "verdict": "non_compliant" }
  ],
  "expected_version": 3
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `verdict` | ✅ | `qualified` / `unqualified`（枚举校验，不再是自由字符串） |
| `comment` | ✅ 判定不合格时必填 | 裁定依据；合格时可填「同意 AI 结论」 |
| `rerun` | 判定不合格时必填 | `true`=驳回重跑；`false`=直接落定不合格 |
| `match_revisions` | 可选 | 逐条条款判定修订（复用现有对话框能力） |
| `expected_version` | 可选 | 乐观锁：防两人同时裁定（409） |

**响应**：返回更新后的 `human_verdict` / `reviewed_by` / `reviewed_at` /
`is_final` / `current_state`，便于前端即时反映。

**为什么把 `match_revisions` 合并进来**：现在的流程是「改条款判定 → 提交并重新执行」，
修订与裁定原本是两步；合并后一次提交即完成「修订 + 裁定 + 签发/驳回」，
避免出现「改了条款但没裁定」的中间态。

  与 SRS 的「裁定」「签发」用语一致；
- 判定不合格时**必须填依据**，前端与后端双重校验；
- 与机器结论不一致时给出提示：「AI 判定为『合格』，你正在判定『不合格』，
  该分歧将记入模型迭代样本」——**这正是 FR-JDG-06 要的样本**。

### 3.6 留痕与审计

每次裁定写两条记录：

| 表 | 内容 |
| --- | --- |
| `human_feedback` | `action=qualified/unqualified`、`dimension=null`（整体结论）、`comment`、`user_id` |
| `audit_log` | `AuditAction.REPORT_SIGN`、`object_type=eval_report`、`object_id`、`detail={verdict, rerun, is_final}` |

**为什么两处都写**：`human_feedback` 面向 FR-JDG-06 的样本归档，
`audit_log` 面向 FR-SYS-03 的合规审计。二者受众不同，不合并。

## 5. 迁移与兼容

**迁移脚本 `0004_human_verdict.py` 必须幂等**（见 `backend/alembic/README.md`）：

```python
def upgrade() -> None:
    bind = op.get_bind()
    columns = {c["name"] for c in sa.inspect(bind).get_columns("eval_report")}
    if "human_verdict" not in columns:
        op.add_column("eval_report", sa.Column("human_verdict", sa.String(16)))
    if "review_comment" not in columns:
        op.add_column("eval_report", sa.Column("review_comment", sa.Text()))
```

**存量数据兼容**：

- 已完成的报告 `human_verdict` 为 `NULL`，语义 = 「未经人工裁定」；
- **不要**批量把存量报告置为 `qualified` —— 那等于伪造签认记录；
- 前端对 `NULL` 显示「未复核」，导出时标注「未经人工复核」。

| 1 | **判定不合格后怎么处理？** | A 一律驳回重跑 / B 可选「驳回重跑」或「直接落定不合格」 / C 只能直接落定 | **B** —— 材料不足类问题重跑无意义，应允许直接落定 |
| 2 | **已签发的报告能否改判？** | A 不可改（需新建修订版报告） / B 可改判但保留历次记录 / C 管理员可改 | **B** —— 监理常有「复核后发现遗漏」，硬性不可改会逼人绕过系统 |
| 3 | **评分达标（≥4.0）的报告要不要也人工签发？** | A 全部需签发（最严） / B 仅低分/降级需签发（现状扩展） / C 按项目配置 | **B 起步，预留 A/C** —— FR-JDG-05 只强制低分必须复核 |
| 4 | **「合格」是否等于「可对外出具」？** | A 是（`is_final=true` 即可导出正式报告） / B 还需第二人复核（双签） | **A** —— 双签是额外合规要求，先不做，但字段设计要能支持（已有 `reviewed_by`） |
| 5 | **是否需要电子签名/签章？** | A 仅记录账号+时间 / B 需手写签名图片 / C 接 CA 证书 | **A** —— B/C 属合规基建，建议列入上线评估的后续项 |

## 10. 一句话总结

**当前实现缺的不是界面，而是「裁定」这个业务动作本身** ——
系统能识别「需要人来看」，却没有地方记录「人看完判定为合格还是不合格」，
也没有「签发」使报告正式生效的环节。本方案补齐这两点，
并保证**机器结论与人工裁定并存、可对比、可追溯**。
