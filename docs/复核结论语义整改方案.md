# 「复核结论合格」语义混淆 · 功能整改方案

> 问题来源：报告中「复核与签发 → 复核结论：**合格**」，无法判断这是
> 「AI 报告的结果合格」还是「评估项目本身合格」。

---

## 一、问题定性

**这不是文案瑕疵，是数据模型的语义缺失。**

系统中存在**两个不同对象的判定**，却用了**同一个词「合格/不合格」**：

| | 判定对象 | 判定人 | 存储字段 | 当前显示 |
| --- | --- | --- | --- | --- |
| 判定 A | **工程/检验批质量**（符合性） | AI | `eval_report.overall_verdict` | 符合 / 不符合 / 部分符合 |
| 判定 B | **AI 报告本身** | 人工 | `eval_report.human_verdict` | **合格 / 不合格** |

判定 B 的真实语义是「**报告可否对外出具**」，来自 SRS 第 92 行：
质量评估专家的职责是「复核**评估结论**、修订评分、**终审签发**」——
复核对象是**报告与其中的评估结论**，不是工程实体。

但界面上：
- 标签叫「复核**结论**」——「结论」二字让人以为是评估结论（工程质量）；
- 值叫「**合格**」——「合格」在工程语境里天然指质量合格；
- **完全没有出现「报告」二字**。

→ 用户把判定 B 误读成工程质量的结论，是**必然**的，不是偶然。

### 更深一层的设计问题：人工复核其实在做三件事

复核动作同时包含「判定 + 签发」，但界面上只有一个标签：

| 层次 | 含义 | 对象 | 当前承载字段 |
| --- | --- | --- | --- |
| L1 是否接受 | 接受/退回 AI 报告 | 报告 | `human_verdict` |
| L2 质量是否达标 | AI 报告质量合格/不合格 | 报告 | `human_verdict` |
| L3 是否签发 | 能否作为正式依据 | 报告 | `is_final` |

「合格」一词把 L1+L2 混在一起，又和 L3「已签发生效」并列出现，
用户无法分辨哪个是决定性的。

---

## 二、整改原则

### 原则 1：每个结论必须显式标注对象

不许出现裸露的「合格 / 不合格」。要么带对象（「报告复核」「报告结论」），
要么用**动作词**（「接受报告 / 退回报告」）——动作天然绑定对象。

### 原则 2：动作词优于状态词

「接受报告」不可能被误读成「工程合格」；
「复核合格」一定会被误读。**优先用动作描述人的行为。**

### 原则 3：机器结论与人工决定必须成对出现

任何展示人工决定的地方（列表、详情、队列），**同一屏内必须能看到机器结论**。
否则「复核=退回报告」会被误读成「工程不合格」。

### 原则 4：不改数据值，只改语义呈现

数据库 `human_verdict` 存 `qualified | unqualified` **保持不变**：
- 避免破坏性迁移与历史数据兼容问题；
- SRS 与测试用例引用的语义不变；
- 但**显示标签**与**界面结构**全面整改。

## 三、术语规范（整改后的唯一口径）

### 3.1 三层结论的命名

| 层次 | 统一名称 | 判定对象 | 取值 | 标签 |
| --- | --- | --- | --- | --- |
| L1 | **评估结论** | 工程质量（符合性） | Verdict | 符合 / 不符合 / 部分符合 / 证据不足 |
| L2 | **报告复核决定** | AI 报告 | accept / return | **接受报告** / **退回报告** |
| L3 | **报告签发状态** | 报告能否作正式依据 | issued / pending | **已签发** / **未签发** |

### 3.2 术语对照表（旧 → 新）

| 位置 | 现状（有歧义） | 整改后 |
| --- | --- | --- |
| 报告详情 · 分区标题 | 复核与签发 | **报告复核与签发** |
| 报告详情 · 字段 | 复核结论：合格 | **复核决定：接受报告** |
| 报告详情 · 字段 | 复核结论：不合格 | **复核决定：退回报告** |
| 报告详情 · 字段 | 裁定依据 | **复核意见** |
| 报告详情 · 字段 | 签认人 | **复核人** |
| 报告详情 · 字段 | 是否签发 | **签发状态** |
| 报告详情 · 值 | 已签发生效 | **已签发**（+ 副标题「可作正式依据」） |
| 报告详情 · 值 | 未签发 | **未签发**（+ 副标题「不得作正式依据」） |
| 报告详情 · 顶层提示 | 该报告已被人工复核判定为不合格 | **该报告未通过复核，未予签发** |
| 报告列表 · 列名 | 总体结论 | **评估结论**（副标题「AI 对工程质量」） |
| 报告列表 · 列名 | 复核 | **报告复核** |
| 报告列表 · 值 | 不合格（指被退回） | **已退回**（避免与工程质量混淆） |
| 复核队列 · 列名 | 裁定 | **复核裁定** |
| 复核队列 · 按钮 | 判定合格 | **接受并签发** |
| 复核队列 · 按钮 | 判定不合格 | **退回报告** |
| 复核对话框 · 标题 | 判定合格并签发 | **接受报告并签发** |
| 复核对话框 · 标题 | 判定不合格 | **退回报告** |
| 复核对话框 · 单选 | 直接落定不合格 | **直接结束（报告不予签发）** |
| 复核对话框 · 单选 | 驳回重跑 | **退回并重新评估** |
| 状态标签 | 已复核不合格 | **已退回** |

### 3.3 关键文案（必须带对象）

| 场景 | 文案 |
| --- | --- |
| 评估结论分区 | **评估结论**（AI 对工程质量的判定） |
| 报告复核分区 | **报告复核与签发**（人工对 AI 报告的取舍） |
| 分歧提示 | 人工复核决定与 AI 评估结论**结论不同**：本报告接受的是「不符合」的评估结论，即**工程质量判定为不符合**，报告已按此结论签发。 |
| 复核对话框顶部 | 本操作复核的是 **AI 生成的报告**，不是重新判定工程质量。工程质量结论已由 AI 给出并将在报告中完整保留。 |

## 四、界面整改

### 4.1 报告详情页（三层分离）

```
┌─ 评估结论（AI 对工程质量）────────┐┌─ 报告复核与签发（人工对报告）────┐
│ 总体结论  不符合                  ││ 复核决定   接受报告              │
│ 风险等级  高                      ││ 复核人     李慧敏 · 2026-10-10  │
│ 依据条款数 5                       ││ 签发状态   已签发（可作正式依据）│
│ 问题项数   5                       ││ 复核意见   已逐条核对引用条款…   │
└───────────────────────────────────┘└──────────────────────────────────┘
   ↑ 机器判定：工程/检验批质量          ↑ 人工决定：这份报告能否出具

                  ── 判定对象不同，结论可并存、不矛盾 ──
```

关键改动：
1. 两个分区的标题**显式写明对象**（「AI 对工程质量」/「人工对报告」）；
2. 两栏之间加一行说明「判定对象不同，结论可并存、不矛盾」；
3. 复核决定的取值改为**动作词**（接受报告 / 退回报告）；
4. 签发状态加副标题说明后果（可作正式依据 / 不得作正式依据）。

### 4.2 报告列表页（防止单看一列被误导）

- 「总体结论」→ **评估结论**，列头加副标题「AI 判定工程质量」；
- 「复核」→ **报告复核**，列头加副标题「人工判定报告」；
- 值「不合格」→ **已退回**（并加 tooltip「报告未通过复核，未予签发」）；
- 保证两列**同时在视口内**，用户不会只看到一列。

### 4.3 质量评审队列

- 列名「裁定」→ **复核裁定**；
- 按钮「判定合格 / 判定不合格」→ **接受并签发 / 退回报告**；
- 表格已有 Judge 评分列，保留（评分是报告质量维度，与工程质量不同，需在列头注明）。

### 4.4 复核对话框

- 顶部 alert：「本操作复核的是 **AI 生成的报告**，不是重新判定工程质量」；
- 标题：「接受报告并签发」/「退回报告」；
- 「裁定依据」→ **复核意见**；不合格时占位符说明「必填：说明**报告**哪里不可接受」。

## 五、数据库兼容（无需迁移）

| 字段 | 处理 |
| --- | --- |
| `human_verdict` | **不变**（`qualified`/`unqualified`）。显示层映射为「接受报告」/「退回报告」 |
| `review_comment` | **不变**，仅显示名改为「复核意见」 |
| `overall_verdict` | **不变** |
| `is_final` | **不变** |

理由：字段值语义本身没错，错在呈现。**不做破坏性迁移**，
避免历史数据与 SRS 引用、既有测试全部需要改动。

同时新增**术语表**（`docs/术语规范.md`），明确「判定对象」约定，
防止后续开发再次引入同类歧义。

## 六、验收标准

| 编号 | 验收点 | 方式 |
| --- | --- | --- |
| A1 | 报告中不再出现裸露的「复核结论：合格/不合格」 | 浏览器检查报告详情 |
| A2 | 复核决定显示为「接受报告」/「退回报告」 | 浏览器检查 |
| A3 | 详情页任一屏内**同时可见**评估结论与报告复核 | 浏览器断言 |
| A4 | 列表页列头带对象说明（AI 判定工程质量 / 人工判定报告） | 浏览器断言 |
| A5 | 两个分区之间有「判定对象不同」的说明 | 浏览器断言 |
| A6 | 复核对话框说明「复核的是报告，不是工程质量」 | 浏览器断言 |
| A7 | 「未签发」报告有「不得作正式依据」警示 | 浏览器断言 |
| A8 | **关键场景**：机器结论「不符合」+ 人工「接受报告」时，界面不产生「工程合格」的误读 | 人工评审 + 截图 |
| A9 | 测试用例覆盖新标签映射 | pytest |
| A10 | 术语表落地，后续开发有据可依 | 文档评审 |

### 关键验证场景（A8）

构造「AI 判不符合 + 人工接受报告并签发」的组合，确认界面表述为：

> 评估结论：**不符合**（AI 判定工程质量不符合）
> 报告复核：**接受报告** → 报告已签发

而**不能**出现任何暗示「工程质量合格」的表述。

## 八、风险与不做的事

| 风险 | 应对 |
| --- | --- |
| 历史报告 `human_verdict` 为 NULL | 显示「待复核」，不显示「未接受」——避免让人以为被退回 |
| 已发出的报告界面用词变化 | 仅显示层变化，数据与审计不变；导出报告正文不含这些标签 |
| 用户已习惯旧词 | 术语表 + 手册同步更新；旧词在 tooltip 中说明等价关系 |

**明确不做**：

1. **不重命名数据库字段**（`human_verdict` 等）—— 收益低、破坏性大；
2. **不引入新的裁定枚举值**（如「有条件接受」）—— 需求未要求，
   三态已经够用，增加取值会让复核流程复杂化；
3. **不把工程质量判定权交给人工** —— 人工复核的对象是**报告**，
   这是 SRS 的职责划分，不应扩大人工的判定范围。
